# Changes

## Logic review fixes

Every bug below has a check in `back-end/tests/api/step8-regression-tests.py` (B-numbers) or in the UI tests.
`npm run check` in `back-end` runs everything on fresh data; all suites pass.

### Permissions and privacy (API)

| ID | Before | Now |
| --- | --- | --- |
| B1 | `DELETE /inquiries/:id` was outside the auth middleware, so even the superuser got 401 | Route is authenticated; superuser can delete, others get 403 |
| B2 | Any staff member could change any colleague's password, including the Company Admin's, and log in as them | Only the Company Admin manages other accounts; changing your own password needs your current password |
| B3 | Any staff member could deactivate the Company Admin | Only the Company Admin changes account status; nobody can lock themselves out |
| B4 | A Project Manager could create a Company Admin account | Project Managers create client accounts only; admins create staff and clients |
| B5 | Site engineers and storekeepers could edit any project (team, dates, `spent`) | Admin: any field. PM: own projects. FM: budget split of own projects. Site engineer: reported progress only. `spent` is calculated by the server and cannot be typed in |
| B6 | Passwords could be set to 1 character | Minimum 6 characters; plain text only (a ready-made hash is refused) |
| B15 | `POST`/`PATCH /users` returned the bcrypt password hash | Hashes are never returned |
| B17 | Staff could read every private message in their company, edit or delete others' messages, fake the sender, and write to other companies | Messages are visible to sender and receiver only; sender comes from the login; only colleagues and the company's clients can be messaged; only the sender edits or deletes |
| B18 | Staff could read and change colleagues' notifications | Notifications are private; you can only notify people you work with |
| B21 | Company Admins ("Add Project" / "+ New Project") and Project Managers ("+ New Project") could create projects by hand, with a client account, skipping the marketplace, the contract and the mobilization advance | The buttons and their forms are gone (projects can still be edited); `POST /projects` is closed to company roles, and PMs can no longer create client accounts. A project now exists only when a client awards a quotation; the API route is kept for the platform superuser (test data setup) |
| B22 | A site engineer whose tasks on a project were all completed could still claim expenses, request materials and file site reports there; an engineer with no task at all on a project could file site reports on it (the report page even listed every company project) | A site engineer acts on a project only while he has an unfinished task there: expense claims, material requests, site reports, progress updates and receiving stock all require it. One allowance: after finishing, he can still file the site report the PM needs to approve that milestone, until it is approved. Correcting a claim the PM returned is still allowed. His screens list only projects where he has unfinished work and say why when there are none; the storekeeper can only issue material to engineers with unfinished work on that project |
| B19 | A PM could manage tasks on other PMs' projects; reports could be filed in someone else's name or on another company's project | Task changes are limited to the project's own PM (or admin); a report's author is always the signed-in user and its project must belong to the company |

### Money

| ID | Before | Now |
| --- | --- | --- |
| B7 | A PM or admin could change the amount of a bill the client had already accepted, and accepted bills could be deleted | Once the client decides, a bill is locked; accepted bills and the mobilization advance cannot be deleted |
| B8 | Pending bill amounts could be set to anything (the contract cap was only checked on create); a PM could point a bill at another client | Stage bill amounts come from the quotation and cannot be edited; a free-form bill's amount stays inside the contract value; parties never change; PMs cannot create or edit bills |
| B9 | A client could record their own payment as "Cash" with any reference | Clients pay through the demo portal methods (UPI, Card, NetBanking, NEFT / RTGS); the receipt number is generated by the server and the payer's own id is stored separately |
| B10 | Bills on projects without milestones skipped the biller and company checks and took the client from the request | Only the project's FM (or admin) can bill; company and client come from the project; not before the advance is paid |

### Data integrity

| ID | Before | Now |
| --- | --- | --- |
| B11 | Deleting a project with bills and payments left them orphaned and deleted the client account | Projects with bills, payments, expenses, purchase orders, contracts or site reports cannot be deleted (mark them Completed or On Hold); an empty project's tasks and milestones are removed with it |
| B12 | A billed milestone could be reopened, re-priced and deleted; editing a task of an approved milestone silently un-approved it | Billed milestones cannot be reopened, edited or deleted; tasks and site reports of an approved milestone are frozen (reopen an unbilled milestone first) |
| B13 | Seed data: bills on milestones that were never approved, and stage amounts that did not match the quotation | Seed is consistent: billed milestones are approved, stage bills match the quoted amounts less 10% advance recovery, and P002–P004 have their paid advance bills |
| B14 | A user still on a project team could be deleted | Refused with the list of projects; reassign them or set the account inactive |
| B16 | "Today" was the UTC date, so in India between 00:00 and 05:30 today's expenses were "in the future" and dates were a day behind | All business dates use India time (`APP_TIMEZONE`), in the API and in the web app |

### Tests and tooling

- All test suites were out of date (renamed demo accounts, changed workflows) and `run-all-checks.sh` printed
  "ALL CHECKS PASSED" even when UI tests failed. Suites updated, UI results now count, each UI test gets fresh data.
- New: `tests/api/step8-regression-tests.py` (73 checks, one per fixed bug; 19 of them fail on the old code) and
  `frontend-react/tests/pages.smoke.test.jsx` (all 70 pages rendered as their role).
- Request IDs are now attached to every request, response, error and log line.
- Swagger uses the login token (Authorize button) instead of the removed `x-role` header.
- Real READMEs, `npm run check`, API tests moved to `back-end/tests/api/`, package renamed `constructhub-backend`.
